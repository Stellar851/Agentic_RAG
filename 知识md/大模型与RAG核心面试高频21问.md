# 模块一：Agentic RAG 核心算法与高级检索体系（核心必考）

### Q1. 什么是摘要索引（Summary Index）？在什么场景下会使用？

- **面试官提问意图**：考察候选人是否只停留在“切分文本 -> 存向量 -> 相似检索”的初级阶段，是否具备解决 RAG “宏观总结能力差”与“海量文档搜偏”的进阶架构经验。
- **核心原理解析**：
  - 传统分块索引（Chunk Index）将文章切分为 500~800 字符的碎片，导致丢失全局上下文与主旨信息。
  - **摘要索引（Document Summary Index）** 是在文档入库预处理阶段，利用 LLM 为整篇文档（或核心大章节）生成高信息密度的全局概括，并针对该“摘要”独立构建向量嵌入与元数据。
- **高分答题模板**：
  > “我们在项目中将摘要索引主要应用于四大典型业务场景：
  > 1. **宏观概括型问题支持**：当用户提问‘*总结这份规范的核心要点*’或‘*该临床试验报告的主要风险是什么*’时，传统微观切片无法拼出全貌，摘要索引可一次性命中全局高密度语义，支撑宏观高质量回答；
  > 2. **海量文档的两阶段路由检索（Document Routing）**：在存有数千份异构制度库的场景下，若在百万切片中裸搜，极易被只言片语带偏。我们先用用户 Query 匹配文档摘要，**第一阶段锁定具体是哪份文件**，**第二阶段再深入该文件做细粒度切片检索**，大幅降低跨文档噪声；
  > 3. **多文档跨篇横向对比**：对比两份技术方案的优劣时，先通过摘要索引提取两份文档的结构化画像，再交由 LLM 进行多维度矩阵对比；
  > 4. **Agent 多跳推理的全局目录地图**：在智能体规划阶段，将摘要索引作为 Agent 判断‘该向哪个文档深入调工具’的全局感知地图。”

### Q2. 传统朴素 RAG（Naive RAG）与 Agentic RAG 的本质区别是什么？

- **面试官提问意图**：考察候选人对 RAG 技术演进（Naive -> Advanced -> Modular -> Agentic）的理解深度。
- **对比维度表**：

| 对比维度 | 传统朴素 RAG (Naive RAG) | Agentic RAG (本项目实现) |
| :--- | :--- | :--- |
| **执行流程** | 单向、固定的静态线性流水线 (Query ➔ Retrieve ➔ Generate) | 基于 ReAct 范式的**认知循环与自主规划** |
| **查询词处理** | 原始用户输入直接做 Embedding，含糊不清/代词极易搜偏 | **自主指代消解与 Query 改写**，支持拆分为多子查询 |
| **多跳检索能力**| “一锤子买卖”，单次检索漏掉关键信息即宣告失败 | **自省证据链缺失**，主动发起第 2 跳、第 3 跳深入追查 |
| **上下文感知** | 仅依赖相似度最高的孤立切片，常出现断章取义 | 支持**连续篇章精读（Read Continuous Chunks）** |
| **幻觉控制** | 缺乏反思机制，检索无关时强行基于幻觉胡编乱造 | **无依据不推断**原则，交叉比对多源证据并输出可信溯源链 |

- **高分答题模板**：
  > “传统 RAG 本质是‘无脑检索拼装’，面对跨文档依赖、需要多步论证的问题完全失效。我们在项目中构建的 Agentic RAG 将大模型从单纯的‘文本生成器’转变为‘中枢推理引擎’：通过 LangChain Function Calling 赋予其检索引擎、单篇精读、文档大纲等工具，Agent 在第一跳检索到线索后，能够自主反思事实缺口，主动发起第二跳定向下钻，并对多源证据进行逻辑去冲突，从而彻底攻克了复杂业务场景下的跨文档长链条推理难题。”

### Q3. 向量检索的召回（Retrieval）与重排（Reranking）有什么本质区别？双塔 vs 交叉编码器怎么选？

- **面试官提问意图**：考察搜索/推荐/NLP 领域经典两阶段架构在大模型应用中的落地理解。
- **核心原理解析**：
  - **召回（Retrieval）**：海量初筛，追求**高查全率（High Recall）** 与**极致低延迟**。采用**双塔模型（Bi-Encoder，如 BGE-M3）**。Query 与 Document 分开离线编码，在线仅计算向量余弦/内积，毫秒级从百万级集合中选出 Top-20。
  - **重排（Reranking）**：精细打分，追求**高查准率（High Precision）**。采用**交叉编码器（Cross-Encoder，如 BGE-Reranker）** 或 **大模型认知重排**。Query 与候选切片拼接输入，词与词进行全层 Cross-Attention，精准识别字面相似但逻辑不符的硬负样本（Hard Negatives）。
- **避坑与实战亮点**：
  > “我们在本项目中不仅支持传统重排模型，更创新性地实现了 **Agentic 认知级动态重排**：向量库召回候选切片后，Agent 在思维链（Thought）中对其进行审查；若发现切片关键细节模糊，不会盲目拼接输入，而是直接调用 `read_specific_document` 按物理顺序读取其前后连续切片，实现了‘粗筛召回 ➔ 认知打分 ➔ 上下文延展精读’的完整工程闭环。”

### Q4. 什么是多跳推理（Multi-hop Reasoning）？如何解决多轮对话指代消解与检索词漂移？

- **面试官提问意图**：考察复杂会话状态下的 Agent 稳定性治理。
- **业务案例**：
  - 用户第 1 轮：“*什么是系统 A 的核心架构？*”
  - 用户第 2 轮：“*它的最大并发连接数在哪个配置项里修改？*”
  - （此时若直接拿第 2 句去向量库检索，由于出现代词‘它’，向量匹配严重失真）。
- **工程解决方案**：
  1. **指代消解（Coreference Resolution）**：在触发工具检索前，Agent 结合近期历史会话（Memory），自主将用户意图重写为包含实体全称的完整 Query（例如自动重写为：“*系统 A 最大并发连接数 配置参数*”）；
  2. **多跳迭代执行（Multi-hop Execution）**：
     - **Hop 1**：检索《系统 A 架构说明书》，发现正文提到“*网络层使用自研中间件 B 承载*”；
     - **Agent 反思**：答案仍缺少具体配置项，但发现了关键实体“中间件 B”；
     - **Hop 2**：自主发起第二跳，定向检索《中间件 B 用户手册》，精准命中参数名 `max_worker_connections` 并提取其默认值。

### Q5. 语义切片分块策略（Chunking Strategy）有哪些考量？为何选择 600/100 参数？

- **面试官提问意图**：切片大小直接决定向量库表示质量，考察候选人对分块边界效应与语义完整度的把控。
- **核心逻辑**：
  - **过大（> 2000 字）**：单一向量承载过多主题，语义被稀释，检索相似度偏低，且容易塞爆大模型最佳上下文窗口；
  - **过小（< 150 字）**：缺乏主谓宾与上下文实体，碎片化严重，导致 LLM 断章取义；
  - **本项目黄金配比（600 字符切片 + 100 字符重叠滑动窗口）**：
    - 600 字符大致对应中文技术文档中的 1 个完整自然段落或 1 个接口定义；
    - 100 字符滑动重叠窗口，**确保跨句实体、指代不会在边缘硬生生截断**；
    - 采用优先级递归标点切分：`["\n\n", "\n", "。", "！", "？", "；", " ", ""]`，坚决不在句子中间机械打断。

### Q6. 知识库长期维护中，如何处理同名文件覆盖与同内容副本泛滥？

- **面试官提问意图**：考察候选人是否有企业级生产环境知识库运营维护的实战踩坑经验，而非仅停留在 Demo 阶段。
- **高分解决方案（三层哈希过滤网）**：
  > “我们在向量入库流水线（`vector_store.py`）中设计了基于 **SHA-256 内容指纹** 的查重与生命周期管理机制：
  > 1. **副本拦截（同内容不同名）**：提取清洗后全文计算哈希，若 ChromaDB 元数据中已存在相同 SHA-256，无论新文件名叫什么，直接拦截并不做重复向量计算，杜绝知识库臃肿与冗余召回；
  > 2. **复用索引（完全相同重复上传）**：哈希与文件名均一致时，直接秒级返回现有元数据，零算力浪费；
  > 3. **版本更新（同名文件内容变更）**：检测到同名但哈希不同，触发‘原子性先删后写’：先在向量库中彻底擦除该文档旧版本切片与向量，再写入新切片，彻底避免新老版本条款矛盾导致的幻觉冲突。”

### Q7. 前端引用的参考文档如何做到“精准溯源校验”，避免正文书名号被误识别？

- **面试官提问意图**：考察严谨的防幻觉工程化设计细节。
- **常见翻车缺陷**：很多初级 RAG 系统在前端展示‘参考文档’时，仅仅在回答文本中用正则去抓书名号（例如 `《(.*?)》`）。如果回答中提到了《Java 核心技术》或《阿里巴巴 Java 开发手册》等举例文献，前端就会荒谬地把它展示为知识库参考文件。
- **本项目的双重校验机制（Double Validation）**：
  1. **结构化提取来源头**：Agent 调用工具时，底层只解析标准来源头（如 `【来源 x】文档: 《真实文件名.pdf》`）；
  2. **向量库元数据交集过滤**：提取到的文件名强制与 ChromaDB 中**物理入库的文档清单计算交集**。不在库内的任何外部书名直接剔除，确保前端展示的参考来源 100% 可信可查。

# 模块二：文档解析与数据工程清洗（独家杀手级亮点）

### Q8. 遇到技术文档中复杂的 ASCII 字符框图/架构拓扑图，直接向量化为什么会崩？你们是如何升维清洗的？

- **面试官提问意图**：考察真实场景下的多模态/异构文本清洗能力。技术方案文档中大量存在由 `+---+`、`| 模块 |`、`-->` 组成的字符拓扑图，这是普通 RAG 最大的死穴。
- **痛点分析**：
  - 传统文本切片器按字符数强行切割，架构图会被切成支离破碎的无意义符号片段；
  - 向量模型（如 BGE-M3）根本无法理解 `+---+` 这类符号的空间相对关系，产生严重噪声，不仅搜不准，还会破坏该文档其他文字的检索精度。
- **本项目的解决方案（大模型智能升维重构）**：
  > “我们在数据预处理管道中设计了**大模型升维清洗引擎（`clean_mode="llm"`）**：
  > 1. 当文本通过预检判定包含架构拓扑图时，调用大模型（DeepSeek-V3）对框图进行逆向语义工程重构；
  > 2. 将其升维翻译为**‘文字逻辑说明 + 标准 Mermaid 流程图代码块’**；
  > 3. 重构后的内容既具备极其丰富的文本语义供向量化匹配，又具有严格的拓扑逻辑在前端被 Mermaid 插件无损可视化还原，攻克了字符图表检索灾难。”

### Q9. 如何精准区分“普通目录树”与“真正的闭合系统架构图”，避免无谓调用大模型浪费算力？

- **面试官提问意图**：考察成本控制（Token Cost Optimization）与算法工程落地能力。
- **原理解析**：
  - 很多文档开头有目录树（例如包含 `├─`、`│`、`└─` 符号），如果粗暴判定为“图表”，就会导致每篇文档都调用昂贵的大模型清洗，造成严重的 Token 浪费与入库延迟。
- **本项目阈值算法设计**：
  - 在 `vector_store.py` 的 `has_complex_ascii_diagram` 中设定复合特征约束：
    - 拐角连接符（`+`、`┌`、`└`、`┐`、`┘` 等）出现频次必须 $\ge 4$；
    - 或带有明确流程走向的箭头标识符（`-->`、`==>`、`->`） $\ge 1$；
    - 且图表关键符号在当前段落密度总数 $\ge 30$；
  - 这种多维特征约束完美放行了纵向单线性的目录树，只精准捕捉真正的二维闭合架构图。

### Q12. SSE 流式打字机推送机制是怎么实现的？用户点击“终止回答”时后端如何中止推理？

- **面试官提问意图**：考察 Web 异步高并发、流式推送（SSE vs WebSocket）与网络连接生命周期控制。
- **技术实现要点**：
  1. **SSE (Server-Sent Events) 架构**：
     - 基于 HTTP 协议，轻量、单向、天然抗代理断连；
     - 后端采用 FastAPI `StreamingResponse(event_generator(), media_type="text/event-stream")`；
     - 自定义 LangChain 回调处理器，实时将 `step_start`（思考中）、`token`（正文碎片）、`step_end` 发送至生成器；
  2. **终止回答（Client Abort）机制**：
     - 前端：使用浏览器的 `AbortController`，当用户点击“停止回答”按钮时，执行 `controller.abort()` 立即关闭底层的 HTTP 连接；
     - 后端：FastAPI / Uvicorn 能够感知到客户端连接中断（`request.is_disconnected()`），生成器抛出 `CancelledError`，从而立即停止向大模型下游发起后续 Token 的网络请求，节约昂贵的 Token 算力。

### Q13. 为什么大模型 Web 应用首屏加载或初次交互会有明显延迟？如何针对性做性能优化？

- **面试官提问意图**：考察系统级性能调优、链路耗时分析（Profiling）与全栈工程优化思维。
- **耗时根因拆解**：
  1. **模型显存休眠与冷启动（主要瓶颈）**：像 Ollama 这类本地服务，默认在空闲 5 分钟后会自动将本地向量模型（如 `bge-m3`）从显存卸载到硬盘。若后端健康检查每次都真实调用一次 `embed_query`，就必须等待几 GB 的模型重新加载进显存，产生 1~3 秒卡顿；
  2. **静态资源/外部 CDN 握手阻塞**：前端引入海外 Google Fonts 或 unpkg/cdnjs，国内环境 DNS 解析与 TLS 建立耗时极长；
  3. **Python AI 重型库装载**：`chromadb`、`onnxruntime`、`torch` 底层有庞大 C++ DLL 扩展，进程初始化冷启动需要 1~2 秒；
  4. **首屏并发接口雪崩**：一进入页面同时向后端打 4~5 个重型接口。
- **立竿见影的优化措施**：
  - **健康检查轻量化**：用 Ollama 的轻量心跳接口（`GET /api/tags`，耗时 5ms）替代真实的向量计算推理；
  - **静态资源本地化/国内 CDN 镜像**：字体与 JS 库打包本地或使用国内镜像源；
  - **异步并发与预热**：使用 FastAPI 异步非阻塞特性，并在服务启动（Lifespan）阶段异步完成向量库连接与模型常驻预热。

### Q14. Windows 环境下终端读取系统环境变量经常失败，代码如何设计注册表穿透兜底机制？

- **面试官提问意图**：考察针对 Windows 生产环境的防御性编程与高可用设计。
- **痛点**：在 Windows 操作系统中，新配置的用户环境变量不会自动同步通知给已经打开的 PowerShell / CMD 进程，导致 `os.getenv("Deepseek_key")` 常常读取为 `None`。
- **注册表穿透实现（`models.py`）**：
  ```python
  import winreg
  # 当 os.getenv 失败时，直接通过 Win32 API 穿透读取系统底层注册表
  def _get_env_from_registry(var_name):
      for root in [winreg.HKEY_CURRENT_USER, winreg.HKEY_LOCAL_MACHINE]:
          path = r"Environment" if root == winreg.HKEY_CURRENT_USER else r"SYSTEM\CurrentControlSet\Control\Session Manager\Environment"
          try:
              with winreg.OpenKey(root, path) as key:
                  return winreg.QueryValueEx(key, var_name)[0]
          except Exception:
              pass
      return None
  ```
  该设计保证了用户即便无需重启终端，后端服务依然能 100% 稳定读取到刚配置的 API 密钥。

- **面试官提问意图**：考察现代包管理核心哲学 —— **“声明 vs 锁定（Declaration vs Lock）”** 与 **确定性构建（Deterministic Builds）**。

  > `uv.lock` 锁定了全部 122+ 个直接与间接依赖的**唯一绝对版本号**以及官方生成的 **SHA-256 安全校验哈希**。无论过多久、部署在哪台机器，一句 `uv sync` 还原出来的二进制环境都毫厘不差，彻底终结了‘在我的电脑上能跑，在服务器上报错’的环境漂移问题。”

### Q17. uv sync 是如何通过 dist-info 差集算法感知并清理虚拟环境中外来未登记包的？

- **面试官提问意图**：考察虚拟环境物理存储底层机制（PEP 405/376）与集合论比对算法。
- **底层原理解析**：
  1. **法定白名单**：`uv.lock` 记录了当前项目允许存在的所有合法包名；
  2. **现场盘点**：Python 虚拟环境中，任何工具（无论是 pip 还是手动拷贝）安装包后，都必须在 `.venv/Lib/site-packages/` 目录下放置一个 **`<包名>-<版本>.dist-info`** 元数据文件夹；
  3. **求差集（Set Difference）**：`uv` 以 Rust 毫秒级扫描该目录下的所有 `.dist-info`，与白名单求差：
     $$\text{待清理包} = \text{虚拟环境实有包} - \text{uv.lock 合法白名单}$$
  4. 若发现有未经登记的库（如临时用 `pip install` 装的外来测试包），`uv sync` 判定其为黑户，直接从文件系统中安全卸载删除，保证生产环境的一致纯净。

### Q18. Python 的内置标准库与第三方库在虚拟环境中的底层存储机制有何本质不同？

- **面试官提问意图**：考察候选人对 Python 运行时底层的扎实功底。
- **底层机制区别**：
  - **内置标准库（Standard Library）**：如 `os`、`sys`、`json`、`typing`、`math`。它们直接内嵌于 Python 核心运行时解释器主目录的 `Lib/` 下，所有虚拟环境通过 `pyvenv.cfg` 指针直接共享宿主运行时的标准库，**不需要也不能通过 pip/uv 安装**，删掉虚拟环境它们也依然存在且可用；
  - **第三方库（Third-party Packages）**：如 `fastapi`、`langchain`、`chromadb`。它们是由社区发布在 PyPI 上的外部轮子（Wheel），**必须且只能安装在具体虚拟环境的 `.venv/Lib/site-packages/` 目录下**。一旦删除虚拟环境，这些第三方库随之彻底消失。
