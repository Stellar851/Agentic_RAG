## 一、 核心编排基准与资源配额规约

为了保障超大规模生产集群（单集群规模 >= 1,000 节点，总 Pod 数 >= 50,000）在高并发业务洪峰下的稳定性，集群资源配置实行严格的**“双重限额基准”**：

### 1.1 CPU 与内存配比基准
1. **核心业务容器（Tier-1 交易链路）**：
   - **CPU配比**：`Request : Limit = 1 : 2`（禁止将 CPU Limit 设置过高，防止节点发生 CPU 剧烈争抢引发上下文切换风暴）。
   - **内存配比**：`Request : Limit = 1 : 1`（生产严禁内存超卖！内存 Request 必须严格等于 Limit，强制将容器的 QoS 级别提升为 **Guaranteed**，彻底免疫节点内存抖动带来的随机驱逐风险）。
2. **边缘与离线任务容器（Tier-3 离线批处理）**：
   - 允许内存 `Request : Limit = 1 : 1.5`，QoS 等级为 **Burstable**。

### 1.2 节点驱逐（Eviction）与内存硬水位阈值
当集群物理计算节点出现资源耗尽时，Kubelet 执行**两阶段梯度驱逐保护机制**：

| 水位级别 | 触发阈值条件 | Kubelet 保护动作 | 处置宽限时限 (Grace Period) |
| :--- | :--- | :--- | :--- |
| **软驱逐阈值 (Soft Eviction)** | 节点可用内存 < 15% 或可用磁盘 < 10% | 停止调度新 Pod 进驻该节点，向平台发送告警 | 宽限观察 90 秒，未恢复则启动排队驱逐 |
| **硬驱逐阈值 (Hard Eviction)** | 节点可用内存 < 5% 或根分区可用空间 < 3% | **立即触发无条件强制驱逐**，直接给 Pod 发送 SIGKILL | 立即执行（0 宽限期） |

## 二、 容器生命周期健康检查与探针治理

所有部署于 Kubernetes 的业务应用，必须严格配置三类健康检查探针，严禁“裸跑 Pod”：

1. **启动探针（Startup Probe）**：
   - 针对 JVM 预热慢或 AI 模型载入慢的服务，配置 `failureThreshold: 30`、`periodSeconds: 10`，最大允许预热冷启动时间为 **300 秒（5 分钟）**。
2. **存活探针（Liveness Probe）**：
   - 探针端点：强制绑定 HTTP `/healthz` 或 gRPC 专用健康检查端口（对应微服务规范中定义的管理端口 `9081`）。
   - 超时与重试：超时时间 `timeoutSeconds: 2`，连续失败 `failureThreshold: 3` 次后，Kubelet 强制重启容器。
3. **就绪探针（Readiness Probe）**：
   - 探针端点：HTTP `/readyz`。一旦连续失败 `failureThreshold: 2` 次，Endpoint 控制器必须在 **1 秒内将该 Pod 从 Service 负载均衡列表中摘除**，严禁将生产流量打入不可用实例。

## 三、 集群核心网络与 DNS 解析性能基线

在大规模高并发微服务调用场景下，CoreDNS 极易成为首要性能瓶颈：

1. **CoreDNS 缓存参数规范**：
   - 内部域缓存 TTL（cache.valid）：统一配置为 **30 秒**；
   - 错误解析记录缓存 TTL（cache.denial）：统一限制为 **5 秒**（防止短时解析失败被长时间缓存导致服务断联）；
   - CoreDNS 实例配置 NodeLocal DNSCache 本地监听代理 IP：`169.254.20.10`。
2. **DNS 并发上限与超时限制**：
   - 单 Pod 解析并发连接上限：`2048`；
   - 单次 DNS 查询超时时间：`2000 毫秒 (2s)`，解析失败重试上限为 **2 次**。

## 四、 跨文档联动与边界处置条款

1. **关联穿透规则**：
   当本规范中的 Pod 发生 OOMKilled（退出码 137）且属于金融核心服务时，监控平台必须联合《01_分布式微服务与金融级容灾架构规范_V3.md》第 3.2 节的断路器策略（熔断阈值 50%），在 30 秒内自动触发降级分流。
2. **违规问责与上线阻断**：
   若业务系统未配置就绪探针或 Request/Limit 超卖比例超过本规范基线，平台 CI/CD 准入网关将直接拒绝部署上线，并自动向平台工程部与研发主管发送 P2 级风险通报。
