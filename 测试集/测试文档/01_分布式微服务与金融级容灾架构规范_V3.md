## 一、 系统架构总体蓝图与单元化设计

### 1.1 单元化架构（Cell Architecture / Set 架构）
为了突破单机房容量上限、实现跨机房故障快速物理隔离，核心交易链路（支付、账户、结算、核心库存）全面实施**单元化架构**：
1. **单元划分准则**：
   - 核心交易单元按**用户 ID（UID）哈希取模 1000** 进行数据分片，划分为 10 个标准业务单元（Cell-01 至 Cell-10）。
   - 全局中心单元（Center Cell）：承载全局唯一数据（如商品主数据、统一机构字典、费率配置）。
2. **机房部署拓扑（同城双活 + 异地灾备）**：
   - **生产 A 机房（上海张江）**：承载 50% 业务单元流量（Cell-01 ~ Cell-05）。
   - **生产 B 机房（上海金桥）**：承载 50% 业务单元流量（Cell-06 ~ Cell-10）。
   - **灾备 C 机房（深圳坪山）**：维持 10% 算力温备，通过专线异步同步底层存储数据，作为冷备兜底。

```
                       [ 全局 GSLB / Anycast 智能 DNS ]
                                      │
               ┌──────────────────────┴──────────────────────┐
               ▼                                             ▼
    【上海张江机房 (DC-A)】                        【上海金桥机房 (DC-B)】
    - 入口网关: Envoy / Ingress                    - 入口网关: Envoy / Ingress
    - 业务单元: Cell-01 ~ Cell-05 (50% 流量)       - 业务单元: Cell-06 ~ Cell-10 (50% 流量)
    - 存储: MySQL MGR 主 + Redis 分布式集群         - 存储: MySQL MGR 从 + Redis 分布式集群
               │                                             │
               └────────────── 专线低延迟直连 (延时 < 1.8ms) ─────┘
                                      │
                                      ▼ (异步增量同步)
                          【深圳坪山机房 (DC-C 异地灾备)】
```

## 二、 容灾可用性 SLA 核心指标

本规范对金融核心链路定义了不可逾越的稳定性红线：

| 指标维度 | 核心交易链路（P0） | 交易辅助与查询链路（P1） | 离线计算与报表（P2） |
| :--- | :--- | :--- | :--- |
| **可用性目标 (Availability)** | $\ge 99.999\%$（全年停机 $\le 5.26$ 分钟） | $\ge 99.95\%$ | $\ge 99.5\%$ |
| **RPO (恢复点目标)** | **$0$**（绝对不允许丢失已确认事务数据） | $\le 10$ 秒 | $\le 1$ 小时 |
| **RTO (恢复时间目标)** | **$\le 15$ 秒**（同城机房级自动切流故障恢复） | $\le 60$ 秒 | $\le 4$ 小时 |
| **跨机房专线延迟上限** | $\le 2.0$ 毫秒（实测基线 $1.65\pm0.2$ ms） | $\le 5.0$ 毫秒 | - |
| **数据同步机制** | MySQL Group Replication (MGR) 强一致半同步 | 异步 binlog 复制 | 每日离线增量抽取 |

## 三、 微服务通讯协议与超时重试策略

### 3.1 通讯协议矩阵
1. **服务间调用（RPC）**：内部微服务通信统一采用 **HTTP/2 over gRPC (Protobuf v3)** 协议，通信端口标准：
   - 内部 gRPC 业务端口：`9080`
   - 内部 gRPC 管理/健康检查端口：`9081`
   - Prometheus 监控抓取指标端口：`9090`
2. **异步事件解耦（Message Queue）**：
   - 削峰与广播事件统一通过 **Apache RocketMQ 5.x** 集群传输，消息存储保证至少 3 副本落盘确认（Sync_Flush + 2 ISR 确认）。

### 3.2 严格超时与重试治理（Timeout & Retry Governance）
严禁任何服务使用客户端框架默认的无限超时。具体参数配置如下：

```yaml
rpc_governance:
  trade_core:
    connect_timeout_ms: 500       # TCP三次握手与连接建立超时: 500ms
    read_timeout_ms: 1500          # 业务执行与读取超时: 1500ms
    max_retries: 2                 # 最大自动重试次数
    retry_interval_ms: 200         # 初始重试退避时间: 200ms
    backoff_multiplier: 2.0        # 退避指数因子 (200ms -> 400ms)
    retryable_status_codes:        # 仅针对网络抖动允许重试，业务异常严禁重试
      - "UNAVAILABLE"
      - "DEADLINE_EXCEEDED"
      - "RESOURCE_EXHAUSTED"
```

> **重要约束**：
> 凡发起重试的请求，请求头中必须强制附带唯一的 `X-Transaction-Id`（UUID v4）以及递增的 `X-Retry-Count`。服务端拦截器必须基于 Redis 分布式锁与业务流水表进行**幂等性防重校验**，防重时间窗口统一设定为 **600 秒**。

## 四、 熔断、降级与过载保护机制

所有核心微服务在集成 Sentinel / Resilience4j 组件时，必须严格套用以下防护规则：

### 4.1 自动熔断降级规则
1. **慢调用比例熔断（Slow Request Ratio）**：
   - 响应时间（RT）阈值定义：`RT > 800ms` 被判定为慢调用。
   - 统计时间窗口：`10 秒`。
   - 触发条件：统计窗口内请求数 $\ge 50$ 且慢调用比例超过 **40%** 时，自动触发熔断。
   - 熔断持续时长：**30 秒**。
   - 恢复机制：30 秒后进入半开状态（Half-Open），放行 10% 试探流量，若连续 10 个请求 RT 均正常则全量恢复，否则重新熔断 60 秒。
2. **异常比例熔断（Exception Ratio）**：
   - 当 5 秒滑动窗口内请求数 $\ge 20$ 且系统级网络异常率（5xx / gRPC Error）超过 **50%**，熔断持续 **20 秒**。

### 4.2 流量过载保护（Rate Limiting & Concurrency）
- 单实例最大并发处理线程数限制：`max_concurrent_requests = 200`。
- 一旦排队队列达到上限（`max_queue_size = 500`），网关层直接对超出流量返回快速失败状态码，禁止在内存中长时间积压。

## 五、 全局系统错误码体系（ERR-5001 ~ ERR-5020）

网关与微服务拦截器统一遵循以下错误码规约，严禁向客户端抛出未捕获的空指针（NPE）或原始数据库异常堆栈：

| 错误码 (Error Code) | HTTP 对应码 | 语义说明 | 客户端应对建议 |
| :--- | :--- | :--- | :--- |
| **ERR-5001** | 504 Gateway Timeout | 下游服务 RPC 调用总耗时超出 1500ms 阈值 | 结合幂等凭证重试一次或轮询订单最终态 |
| **ERR-5002** | 503 Service Unavailable | 触发服务慢调用熔断或下游节点无可用存活实例 | 提示用户“系统繁忙”，稍后重试 |
| **ERR-5003** | 429 Too Many Requests | 触发限流阈值，单 UID 或单 IP 请求频次超限 | 客户端指数退避后重试 |
| **ERR-5004** | 409 Conflict | 并发操作触发分布式锁争抢失败（幂等拦截） | 稍候重新拉取最新数据，勿重复点击提交 |
| **ERR-5005** | 500 Internal Error | MySQL MGR 事务提交失败（跨机房仲裁冲突） | 自动转入异步补偿对账流水 |
| **ERR-5006** | 401 Unauthorized | SPIFFE 证书校验失败或 mTLS 证书已过期 | 检查服务证书挂载与更新代理状态 |
| **ERR-5010** | 400 Bad Request | 请求参数校验未通过（Pydantic/Protobuf 格式校验） | 修正入参数据结构 |
| **ERR-5020** | 502 Bad Gateway | 跨机房专线物理抖动丢包率 > 5% | 触发 GSLB 全局流量向备机房自动切换 |

## 六、 混沌工程与演练标准（Chaos Testing）

根据架构委员会要求，所有进入 P0/P1 等级的系统必须每月执行自动化混沌故障注入演练：
1. **演练项目**：
   - 随机杀死 30% 的 Kubernetes Pod 实例，服务错误率上升不得超过 **0.01%**。
   - 模拟单条同城光纤被挖断（延迟从 1.8ms 突增至 50ms），系统必须在 **10 秒**内完成专线主备倒换。
   - 模拟 MySQL 主库强行宕机，MGR 集群必须在 **12 秒**内完成新 Primary 选主并接管写请求。
