## 一、 零信任核心哲学：从“边界防御”到“持续验证”

在传统网络边界防御体系中，内网往往被假定为安全受信区域，导致一旦边界被横向渗透，攻击者可自由访问全部内部数据。  
零信任架构（Zero Trust Architecture, ZTA）遵循三大绝对公理：
1. **Never Trust, Always Verify（从不信任，始终验证）**：任何网络位置（外网、内网、云专线）的通信均视为潜在恶意。
2. **Least Privilege Principle（最小特权原则）**：仅分配完成当前瞬时操作所必需的最小权限集合，禁止任何通配符权限授权。
3. **Assume Breach（假定已被入侵）**：在架构设计时默认内部节点存在被渗透可能，通过细粒度微隔离与通信全链路加密降低爆炸半径。

## 二、 服务间通信身份标识：SPIFFE / SPIRE 身份标准

### 3.2 节：微服务 mTLS 双向认证与 SPIFFE 证书签发规范（重点章节）
微服务之间的通信必须彻底废除硬编码的 API Key 或静态 Token，全面强制接入 **SPIFFE（Secure Production Identity Framework for Everyone）** 身份体系：

1. **SPIFFE ID 统一命名规范**：
   每个在集群中运行的微服务 Pod / 容器在启动时必须由 SPIRE Agent 动态注入全局唯一的工作负载身份 URI：
   $$\text{spiffe://group.internal/ns/}\{namespace\}\text{/sa/}\{serviceaccount\}\text{/svc/}\{servicename\}$$
   *示例*：支付网关服务在生产机房的 SPIFFE ID 为：`spiffe://group.internal/ns/fin-trade/sa/payment-sa/svc/pay-gateway`

2. **X.509 SVID 证书生命周期**：
   - **私钥加密算法**：强制采用 **ECDSA 椭圆曲线加密（基于 NIST P-256 曲线）**，杜绝使用已被淘汰的 RSA-1024 或容易被侧信道攻击的旧算法。
   - **证书有效周期（Validity Window）**：为了防御私钥泄漏风险，签发的 X.509 客户端/服务端证书有效期严格限定为 **1 小时（3600 秒）**。
   - **自动平滑轮换（Rotation Policy）**：SPIRE Agent 在证书剩余有效期达到 **15 分钟（900 秒）** 时，自动发起后台无感知续签，确保在连接不中断的前提下完成私钥与证书的热替换。
   - **异常响应**：若微服务调用方携带的证书超过 3600 秒或私钥签名校验失败，接收端必须立即阻断连接并向网关返回错误码 `ERR-5006 (Unauthorized)`。

## 三、 企业数据安全四级分级模型（C1 ~ C4）

集团根据数据资产泄露后对企业声誉、财产及用户隐私造成的危害程度，将数据严格划分为四个等级：

| 等级标识 | 数据密级定义 | 典型数据字段举例 | 存储加密策略 | 外发/展示脱敏要求 |
| :--- | :--- | :--- | :--- | :--- |
| **C1** | **公开数据 (Public)** | 企业对外公开新闻、招聘信息、产品公开售价、官方宣传文档 | 无需特殊加密，常规明文存储 | 无需脱敏 |
| **C2** | **内部数据 (Internal)** | 部门内部周报、非涉密会议纪要、普通运维配置模板、公开商品详情 | 数据库标准透明加密 (TDE) | 仅限集团内部工号授权访问 |
| **C3** | **敏感数据 (Sensitive)** | 用户手机号、收货地址、电子邮箱、员工绩效评分、订单交易流水 | 字段级强加密（AES-256 或 SM4） | **强制动态遮蔽（Masking）**后展示 |
| **C4** | **绝密数据 (Strictly Confidential)** | 身份证号、护照号、完整银行卡号、CVV2 安全码、支付密码哈希、用户生物特征（人脸特征向量） | 硬件安全模块 (HSM) 硬件级加密，主密钥不出芯片 | **严禁明文展示与导出**，仅允许返回脱敏后验证状态 |

## 四、 核心隐私字段动态脱敏（Data Masking）执行规约

前端交互、客服工单系统、测试环境拉取及日志采集系统必须挂载动态脱敏切片拦截器，脱敏标准严格执行如下算法规则：

### 4.1 核心脱敏规则算法表
1. **大陆居民身份证号码（18 位）**：
   - 规则：保留前 3 位（省级行政区代码）与末尾 4 位（校验码），中间 11 位用星号 `*` 屏蔽。
   - 掩码示例：`310115199001011234` $\to$ `310***********1234`
2. **手机号码（11 位）**：
   - 规则：保留前 3 位网络运营商号段与后 4 位用户号码，中间 4 位用星号 `*` 屏蔽。
   - 掩码示例：`13812345678` $\to$ `138****5678`
3. **银行卡号 / 信用卡号（16~19 位）**：
   - 规则：保留前 6 位（发卡行 BIN 码）与后 4 位，中间所有卡号连续替换为固定 6 个星号 `******`。
   - 掩码示例：`6222021234567890123` $\to$ `622202******0123`
4. **电子邮箱地址（Email）**：
   - 规则：保留 `@` 符号前的前 2 个字符以及 `@` 之后的完整域名，用户名其余部分替换为 3 个星号 `***`。
   - 掩码示例：`security_admin@enterprise.com` $\to$ `se***@enterprise.com`

## 五、 双密码体系与密钥生命周期管理（KMS）

### 5.1 国际/国密双算法支持
系统架构支持根据部署环境与客户合规要求无缝切换加密套件：
- **政企与金融合规专区（国密标配）**：强制采用国家密码管理局商用密码体系，对称加密采用 **SM4-CBC（128位密钥，PKCS#7 填充）**，摘要算法采用 **SM3（256位散列）**，非对称算法采用 **SM2（256位椭圆曲线）**。
- **公有云海外多区域专区**：对称加密采用 **AES-256-GCM（伽罗瓦计数器模式）**，摘要算法采用 **SHA-384 / SHA-512**。

### 5.2 密钥分级与轮换机制
1. **根密钥 (Root Key / Master Key)**：
   - 存放在符合 FIPS 140-2 Level 3 或国密二级标准的硬件密码机（HSM）中。
   - 轮换策略：系统每年自动执行一次根密钥轮换（周期：**365 天**），旧密钥保留为只读解密状态，持续保存 3 年以兼容历史数据回溯。
2. **数据加密密钥 (Data Encryption Key, DEK)**：
   - 采用信封加密模式（Envelope Encryption），每个独立的业务数据库表或文件块生成独立的 DEK。
   - 单个 DEK 允许加密的数据包次数上限为 **100,000 次**，达到上限后系统自动触发 KMS 签发新 DEK。

## 六、 审计追溯与日志防篡改哈希链

为了满足等保 2.0 三级与金融监管审计追溯要求，系统产生的每一条安全审计日志必须具备不可抵赖性：
- 审计日志在落盘前，必须使用集群密钥计算前一条日志与当前日志的 **HMAC-SHA256 哈希链（Hash Chain）**。
- 哈希链记录格式：
  $$\text{Hash}_n = \text{HMAC}(\text{SecretKey}, \text{Hash}_{n-1} \parallel \text{Timestamp} \parallel \text{OperatorID} \parallel \text{Action})$$
- 任何试图直接篡改数据库或文本日志的行为，均会导致连续哈希验证断裂，安全审计机器人将在 **30 秒**内发出一级安全告警并联动防火墙阻断相关账户。
